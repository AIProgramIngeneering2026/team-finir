# Правила работы над проектом

## 1. Ветки

- `main` — стабильная ветка: код в ней собирается и проходит тесты.
- В `main` ничего не пушим напрямую — только через Pull Request.
- Для каждой задачи — своя ветка от актуального `main`.
- Название ветки: `<тип>/<кратко-о-задаче>`, латиницей через дефис.
- Типы: `feature`, `fix`, `docs`, `test`, `refactor`, `ci`.
- После слияния ветка удаляется.

Примеры: `docs/requirements`, `feature/gomod-parser`, `feature/osv-client`, `fix/scan-cancel`.

## 2. Коммиты

- Каждый коммит содержит логически завершённое изменение: после него проект собирается и тесты проходят.
- Сообщение короткое и понятное: тип изменения и что было добавлено или исправлено.
- Тип — тот же, что у ветки: `feature`, `fix`, `docs`, `test`, `refactor`, `ci`.
- Если причина изменения не очевидна, её пишем в теле коммита через пустую строку.

Примеры:
- `docs: описание проекта и сценарии`
- `feature: модель скана и проверка переходов`
- `feature: разбор go.mod с учётом replace`
- `fix: повтор запроса к OSV.dev при таймауте`

## 3. Pull Request и review

- В описании PR пишем, что изменено и как это проверить. Если есть связанный Issue — добавляем `Closes #N`,
  чтобы он закрылся при слиянии.
- Перед открытием PR автор сам запускает проверки из раздела 4.
- PR вливается через **Squash and merge**, чтобы в `main` была понятная история: один коммит на задачу.

**Review:**
- Если в команде несколько участников, PR проверяет другой участник.
- Смотрим не только на то, работает ли код, но и на понятность имён, обработку ошибок, наличие тестов
  на ошибочные случаи. Ориентир — [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments).
- Замечания оставляем к конкретным строкам. Мелочи, которые можно не исправлять, помечаем `nit:`.
- Пока в команде один участник, автор сам проверяет изменения по разделу 4 перед слиянием.
- После проверки и устранения замечаний PR сливается в `main`.

## 4. Definition of Done

Задача считается выполненной, если:

1. Выполнены требования и критерии приёмки из Issue или [docs/requirements.md](docs/requirements.md).
2. Код отформатирован `gofmt`, `go vet` и `golangci-lint` не находят проблем.
3. Тесты проходят с флагом `-race`. На новое поведение есть тесты, включая ошибочные случаи.
4. Ошибки не игнорируются и возвращаются с контекстом: `fmt.Errorf("parse go.mod: %w", err)`.
5. После `go mod tidy` файлы `go.mod` и `go.sum` не меняются.
6. Документация обновлена, если изменилось поведение: `README.md`, `docs/`, `docs/api/openapi.yaml`.
7. Секретов в репозитории нет, настройки берутся из переменных окружения.
8. CI проходит, изменения слиты в `main`, Issue закрыт.

## 5. Организация работы

- Задачи заводятся в GitHub Issues, у каждой есть исполнитель.
- Перед началом работы исполнитель назначает себя на Issue и создаёт ветку.
- Когда в команде появятся новые участники, задачи распределяются между ними.
- Правила работы могут уточняться по мере развития проекта — через Pull Request в этот файл.
