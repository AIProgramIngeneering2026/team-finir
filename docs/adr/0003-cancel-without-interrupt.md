# ADR-0003. Отмена скана без прерывания работы

**Дата:** 2026-11-08
**Статус:** принято

## Контекст и ограничения

- Клиент может отменить скан, который уже выполняется: загрузил не тот файл, PR закрыт.
- Скан длится секунды; дольше только при медленном OSV.dev — до суммарного таймаута с повторами.
- API и воркеры работают в одном процессе (ADR-0001).
- Отменённый скан не должен публиковать отчёт.

## Решение

- Скан в `created` отменяется сразу: атомарный переход `created → cancelled`, воркер его не возьмёт.
- Выполняющийся скан помечается флагом `cancel_requested`, обработка не прерывается.
  В конце воркер одним условным обновлением выбирает итог: если флаг стоит — `cancelled`,
  отчёт не сохраняется; иначе — `done` или `partial`.
- Отмена завершённого скана → `409 scan_finished`.

## Рассмотренные альтернативы

| Альтернатива | Почему нет |
|---|---|
| Прерывать через `context`, воркер раз в секунду опрашивает флаг в БД | лишние запросы к БД ради выигрыша в несколько секунд; гонки при отмене посреди сохранения |
| Реестр выполняющихся сканов в памяти, API вызывает `cancel()` | мгновенно, но работает только в одном процессе; больше кода ради коротких сканов |
| `LISTEN/NOTIFY` в PostgreSQL | нет в SQLite, который используем на прототипе |
| Не поддерживать отмену | клиент не может остановить скан ошибочно загруженного файла |

## Цена решения

- После отмены запросы к OSV.dev продолжаются, пока скан не доработает. Детали уязвимостей при этом
  попадают в кэш, так что работа не совсем пропадает.
- Скан переходит в `cancelled` не сразу, а после завершения обработки: при недоступном OSV.dev —
  через время таймаута и повторов.

## Условия пересмотра

- Сканы станут долгими (минуты) или дорогими → прерывание через `context` и реестр в памяти
  (или `LISTEN/NOTIFY` после перехода на PostgreSQL).
